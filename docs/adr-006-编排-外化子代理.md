# ADR-006：编排——把 agent 的子代理外化为可观察的真实会话

日期：2026-08-14　状态：已采纳

## 背景

claude 在工作中会用内部 Task 工具拉起子 agent，这个过程对用户是黑盒——界面上只有一个工具调用卡片，派了什么任务、子 agent 每一步做了什么都看不到。用户的核心诉求：**让 agent 需要子代理时改走我们系统**——我们拉起真实的 ACP 子会话充当子 agent，派发内容、工作过程、返回结果全部成为可观察的一等公民。

明确不做「团队」实体（曾经的候选形态）：不预组常驻成员，子 agent 按需雇佣、用完即收；承载界面是**独立的编排对话页**，现有会话功能保持原样。

## 实测依据（全部真机验证，2026-08-14，runtime 版本 claude-agent-acp 0.63 / codex-acp 1.1.7）

1. **MCP 挂载**：两端 `mcpCapabilities.http: true`。HTTP MCP server 经 `session/new` 的 `mcpServers` 传入后，两端都能列出并真实调用我方工具。
2. **同步 spawn（工具调用挂起等子任务）**：claude 默认约 2 分钟超时，设进程 env `MCP_TOOL_TIMEOUT`（毫秒）后 150s 挂起实测成功；codex 经 `session/new` 传入默认即挂 150s 成功，且可完全从 `CODEX_HOME/config.toml` 定义 MCP server（带 `tool_timeout_sec`），`session/new` 不传。
3. **角色注入**：claude 走 `session/new` 的 `_meta.systemPrompt`——对象形式 `{append}` 保留 claude_code preset 只追加；codex 无协议注入口，走 per-角色 `CODEX_HOME/AGENTS.md`。均实测生效。
4. **收口内部子代理**：claude 的 `_meta.claudeCode.options.disallowedTools` 与内置清单合并，传 `["Task"]` 即禁用内部子 agent；codex 无实用内部子代理机制，无需收口。
5. **AI 间无直连通道**：ACP 会话是被动的，一切「派发/汇报」都必须经我们后端中转——这正好让全部通信天然可观察、可记录。

## 决策

### 形态

- **角色**（导航「角色」，路由 `/roles`，避开已退役的 `/agents`，见 adr-005）：全局资产。角色 = 名字 + 职责简介（给主会话的雇佣目录看）+ persona 提示词 + 绑定工具（claude/codex）+ 模型/思考深度 + 权限档。内置分析员/开发者/审查者/测试员模板，可改可增。
- **编排会话**（导航「编排」）：独立对话页。主会话挂载我方 MCP server 并注入调度提示词（含可用角色清单）；claude 主会话追加 `disallowedTools:["Task"]` 与 `MCP_TOOL_TIMEOUT`。
- **spawn 生命周期**：主会话调用 `spawn_agent(role, task)` → 后端建任务记录 + 拉起子会话（角色注入，权限档按角色）→ 同步等子会话 turn 结束 → 最终回复文本作为工具结果返回主会话。失败/中止返回错误文本，主会话自行决策。子会话记录与转录保留可追溯。
- **UI**：dockview 布局。主对话面板 + **常驻 task 列表面板**（角色、任务摘要、状态、耗时，实时更新）。子会话**不自动弹出**——用户从列表拖出成对话面板（可多个、自由布局），关闭面板只回列表、任务照跑。另有急停（中止主 + 全部在跑子任务）。

### 隔离契约（对现有会话零影响的硬承诺）

| 层 | 方案 |
| --- | --- |
| 数据库 | 新表 `roles` / `orch_sessions` / `orch_tasks`，不动 `sessions` 表 |
| 业务层 | service 包内新文件族（orch*/role*），不改 ChatService/SessionService；broker、重建器、SSE 事件映射等**包内无会话语义的构件**复用 |
| API | 新前缀 `/api/orchestrator/*`、`/api/roles`、`/api/mcp/{token}`；`/api/sessions/*` 原样 |
| ACP 层 | 复用 `acp.Manager`（key 空间 `orch-*` / `orchtask-*`，与数字 key 的普通会话并存——`probe-agent-N` 已有先例）；`OpenOptions` 只增字段（ExtraEnv/MetaExtra），不传时行为不变 |
| 前端 | 新路由页 + 新 hook（use-orch-chat），不改 use-chat 与 sessions 一族；纯渲染组件按 props 复用 |

删除整个编排功能不影响普通会话——这是隔离是否成立的检验标准。

### 关键实现选择

- **MCP server 自实现**（不引 SDK）：协议面只需 initialize / tools/list / tools/call 三个方法的 JSON-RPC over HTTP POST，百行量级；挂 `/api/mcp/{token}`，token 为每编排会话随机生成——既标识身份也做隔离（子会话拿不到，天然深度 1）。
- **codex 主会话用专属 codex-home**（`<dataDir>/orch/homes/...`）：config.toml = 系统副本 + acpp MCP server 定义（url 含 token）+ `tool_timeout_sec`。不能写共享 codex-home 的 config——那会让普通 codex 会话也连上编排 MCP（污染）。
- **子会话不挂 MCP**：spawn 深度硬性为 1，防递归失控。
- **护栏**：并发子任务上限；单任务硬超时（我们侧兜底）；急停；编排会话累计 token 用量（主 + 子）展示。

## 后果

- 编排侧的轮次执行/SSE 流与 ChatService 存在少量相似逻辑，第一版接受这份重复换隔离，稳定后再评估抽公共件（不顺手重构现有代码）。
- claude 角色的「只读」边界是 SDK 级（权限档 + 工具禁用），Bash 写文件拦不死；codex 的 read-only 沙箱是 OS 级。角色能力边界是纪律边界而非安全边界，文档如实声明。
- MCP 工具调用挂起期间 agent 侧无进度概念，长任务全凭我方 UI 展示子会话过程；`MCP_TOOL_TIMEOUT`/`tool_timeout_sec` 取大值（30 分钟），超过的由我方硬超时先行了断并返回错误。
