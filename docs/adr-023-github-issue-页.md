# ADR-023：GitHub issue 页

日期：2026-09-10　状态：已采纳

## 背景

团队的任务在 GitHub issue 上流转：分配、优先级（issue 侧栏 Fields 的 Priority）、进度（Project 看板的 Status 列）。要看「我手上有什么、哪个最急、走到哪一步了」得在 GitHub 上翻几个仓库、几块看板。用户此前用一个独立的菜单栏小程序（codex-ui）汇总 issue，它验证了一条可行的取数路径：本机 gh CLI 拉列表，GraphQL 从 issue 这头反查 Priority 与看板 Status，不需要配置看板编号。

acpp 已经是团队每天开着的面板，而且有多租户：局域网里的每个人各有身份。把 issue 汇总搬进来，每个人看自己的。

## 决策

1. **一个列表页，与其他列表页同一副四区骨架**（搜索 / 操作 / 表格 / 翻页）。列：项目、编号、标题、标签、优先级、状态（= 看板列）、更新时间。**默认条件**：分配给我、open、看板列排除做完 / 取消的、按优先级排（紧急在前，同档更新时间新的在前，没优先级的垫底）。PR 不做——用户明确先只要 issue。**2026-09-10 补记**：同档改为按仓库、编号升序——编号就是创建顺序，先建的先做；按更新时间会让一条评论就把清单重排，菜单栏面板里尤其晃眼。
2. **取数全部经 owner 本机的 gh**。租户没有自己的 GitHub 凭证，也不该有（那是 owner 钥匙串里的东西）；「分配给我」靠访客记录上的 `githubLogin` 筛，由 owner 在访客管理里填。仓库清单也是 owner 账号能看到的全部（含个人名下的——与克隆刻意不同，自己的仓库正是最常关注的）。
3. **每个身份各存一份关注清单**（`GithubWatch`，`tenantId` 0 = owner，与 Session 同一约定），页面只汇总关注仓库的 issue。owner 不入 tenants 表，所以这张表的键不能是外键。
4. **issue 不落库**：按仓库缓存在内存里，后台每 3 分钟刷新所有被关注的仓库；过滤 / 排序 / 分页在内存里做。一个仓库几百条 issue 对这套操作不算数据量，落库只会多一层「缓存的缓存」要同步。进程重启就重拉——首次打开等一下，等到的是真数据。
5. **看板列与优先级档的词汇表跟着数据走**：Status 的全集与顺序取自 issue 所在 Project 的字段定义，Priority 取自仓库的 issueFields 定义，随 issue 一起返回给前端画筛选器。名字是用户自定义的（待处理 / 进行中 / 待验收 / 已完成 / 已取消），后端不硬编码；「做完了」的列按名字认（完成 / 取消 / 关闭 / done / closed / cancel）。
6. **桌面壳的菜单栏也列同一份清单**：右键菜单里「我的 issue」直接调 `/api/github/issues`（owner 回环、无凭证），条件与页面默认一致，最多 15 条，点一条打开 GitHub。**2026-09-10 补记**：图标改成左键弹 issue 面板、右键才是操作菜单。面板不用 Electron 原生菜单——它只能放文字，画不出 codex-ui 那种色点 / 状态徽标 / 行内按钮 / 点编号闪「已复制」的行——而是自绘：`vibrancy: "menu"` 的非激活式 NSPanel（`type: "panel"`，弹出不激活整个 app、主窗口不会被拽到前台）贴在图标下方，页面在 `desktop/electron/popover/`，数据经 `preload/popover.cjs` 的窄通道从壳里拿。点行开 GitHub，点编号**复制纯数字编号**（把编号丢给 `/issue` 命令是最高频动作），与 codex-ui 的分工一致。「用哪个 Chrome 账号打开」是壳自己的偏好（`prefs.json`），不进服务端——那是这台机器的浏览器，不是服务配置；实现照 codex-ui：直接跑 Chrome 二进制传 `--profile-directory`，`open -a` 在 Chrome 已运行时会把参数整段丢掉。
7. **gh 封装提为叶子包 `ghcli`**：project（仓库清单）与 github 两处要跑 gh，找路径（打包成 .app 后 PATH 里没有 homebrew）与译错误（「没装」「没登录」）不该各写一份。gist 包的 gh 调用有自己的一套错误文案（gist 权限），这次不动。

## 理由

- **对外接口少**：两个端点（`/api/github/issues`、`/api/github/repos`），看板列、优先级、标签词汇表都塞在列表响应里，前端不用先问一遍「有哪些列」再查列表。
- **租户可用但不越权**：租户看到的是 owner 账号视角下的公共信息（issue 标题、分配、看板），不含凭证，也不能写 GitHub。这与数据库只读面（adr-021）同一姿态。
- **不做 PR**：PR 的取数（我创建 + 待我审两路合并、CI 状态）是另一套形状，用户先不要，留着只会拖慢 issue 这一半。

## 后果

- 新包 `ghcli`、`github`；新表 `github_watches`；`tenants` 加 `github_login` 列。
- 后台每 3 分钟对每个关注仓库打两次 GitHub 请求（列表 + GraphQL），关注十个仓库也远在配额之内。
- 看板列名靠正则认「做完了」，起了个不常见的名字（比如「归档」）就不会被默认排除；用户可以在「看板」筛选里自己选。
