# ADR-017：Discord 子区对话——@bot 开子区，子区里直接与 acp 干活

日期：2026-08-28　状态：已采纳（建立在 [adr-016](adr-016-discord-频道工作区.md) 的频道绑定之上）

## 背景

adr-016 落地了频道 ↔ 仓库工作区的绑定（/init、克隆、模型/思考深度/安全
权限档、频道主题为唯一常驻信息面）。本篇是对话面，用户定的工作逻辑：

1. 绑定频道里 `@bot <问题>`；
2. bot 以那条消息开一个子区（主频道保持干净，只见子区标题）；
3. 子区里直接与 acp 对话——工作目录就是绑定的克隆，模型/思考深度/权限
   档全部沿用绑定（/model /effort /access 随时可改）。

## 决策

### 1. 直接用 internal/acp，但开独立会话池

「不使用会话的一针一线」指的是会话体系（service 层的 Session/Chat/转录/
SSE）；`internal/acp` 是叶子协议客户端（与 gitrepo 同性质），discord 直接
import。但会话池**独立**（`chatMaxSessions=4`、轮超时 30 分钟、空闲 20
分钟回收）——与网页会话池互不挤占，discord 的资源边界自己管。agent 的
启动方式（命令/参数/环境）经 `Deps.AgentRuntime` 注入，包仍不认识
model/db。技能包注入与网页会话同一份（SkillpackDir）。

### 2. 对话记录不落库——Discord 就是转录

子区本身就是完整的对话记录，不进 acpp 的转录体系、不在网页会话列表出现。
唯一落盘的是 `threads`（子区 id → acpSessionId，存 discord.json）：子进程
被空闲回收或服务重启后，凭它 `session/load` 无感恢复上下文。

### 3. 排队式回合，不用 Interject

回合进行中的追加消息**排队**，当前轮结束后合并成下一轮输入。刻意不用
acp 的 Interject——它在两个 runtime 上语义不同（claude 排成独立新轮、
codex 注入当前轮），排队的行为可预期且实现只有一把锁。

### 4. 频道里只出正文

思考、工具调用、计划都不发（频道干净原则）；回合期间用 typing 指示器
（8 秒续一次）表达「在干活」。轮末把正文按 1900 字分段发出，代码围栏被
切开时每段补闭合、下段重开。纯工具轮（没有正文）发一行结束原因。
`/stop` 中止当前回合并清空排队输入。

### 5. 权限与提问走「编号问答桥」

safe 权限档的授权请求、agent 的主动提问（AskUserQuestion 类），都转成
子区里的编号列表消息；**子区的下一条用户消息优先当作答**（编号选选项，
提问也接受自由文本）。多题表单在文本流里问不清楚——诚实取消并提示去
网页版，不让回合挂死。

### 6. 子区归属的判定与收养

MESSAGE_CREATE 不带 parent 信息，第一次见到的 channel id 现查一次 REST
（结论含负缓存）。绑定频道下**用户手动开的子区同样收养**——判定标准是
「绑定频道的子区」而不是「bot 开的子区」。

## 后果

- gateway intents 加 GUILD_MESSAGES + MESSAGE_CONTENT（特权 intent，
  开发者门户已开）。
- 主频道的非 @ 消息一律不响应；未绑定频道的 @ 同样沉默。
- 绑定改仓库后，已开的子区会话仍在旧 cwd 上（会话粘住打开时的目录）；
  子进程回收后的下一轮才落到新目录。可接受——重绑是低频动作。
- 单条回合上限 30 分钟（含挂起的问答），超时按失败回报。
