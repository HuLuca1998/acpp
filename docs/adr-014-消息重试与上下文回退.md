# ADR-014：消息重试与上下文回退

日期：2026-08-24　状态：已采纳

## 背景

会话出错时（最常见的是 `API Error: 529 Overloaded` 这类与内容无关的服务端过载），
用户此前唯一的出路是把同一段话手动复制、再发一遍。代价有三个：

1. 原文很长时重发很烦，附件与 `@` 引用还得重新挑一遍；
2. 转录里出现两条一模一样的 `session/prompt`，重建后界面上就是两个重复气泡
   （会话 105 就是这个样子）；
3. 失败那一轮的残留内容（半截回答、报错文本）留在 agent 的上下文里，
   重发等于「带着上次的失败痕迹再来一遍」，而不是干净地重跑。

目标：给出一个重试入口，做到**不必重新输入**、**界面上不留重复**、
**尽可能让 agent 侧的上下文也回到那条消息之前**。

## 协议现状（2026-08-24 实测）

ACP 标准里没有「回退到某条消息」的能力：

- `session/fork` 的参数只有 `sessionId / cwd / additionalDirectories / mcpServers / _meta`，
  没有任何截断字段，官方注释说它的用途是「基于现有上下文开个新会话，
  比如生成摘要而不污染原历史」；`session/load`、`session/resume` 同样没有。
- 两端 `initialize` 声明的 `sessionCapabilities`：claude 有 `fork`，**codex 没有**。
- codex-acp 调用的 app-server 方法全集是 `thread/{start,resume,read,list,archive,compacted}`
  与 `turn/{start,steer,interrupt,completed}`，没有任何回退/分支能力。

但 claude 的底层 SDK 有：`@anthropic-ai/claude-agent-sdk` 的 query 选项
`resumeSessionAt`（*"only resume messages up to and including the message with this UUID"*）
与 `forkSession(sessionId, {upToMessageId})`。ACP 适配器不主动用它们，
却把 `_meta.claudeCode.options` **整体展开**进 SDK options
（`acp-agent.js` 的 `const options = { ...userProvidedOptions, … }`），
于是客户端可以借道用上。

## 决策

**claude 会话走 `_meta.claudeCode.options.{resume, resumeSessionAt}` 做真回退，
codex 会话降级为原地重发，两者共用同一套「界面不留重复」的机制。**

实现分三块：

1. **id 映射**（`server/internal/acp/claude_rewind.go`）。ACP 暴露的 `messageId`
   是 Anthropic API 的 message id（`msg_xxx`），而 `resumeSessionAt` 只认 claude
   自己转录里的条目 `uuid`。对照表只存在于 `~/.claude/projects/<项目>/<会话id>.jsonl`
   里，按会话 id 的文件名去找（目录名的转义规则没有文档承诺，不去推算路径）。
2. **回退开会话**（`ChatService.openWith`）。截断参数只有 `session/new` 会读，
   所以这条路要先关掉现有连接、并且不能带 `ResumeACPSessionID`（那会走
   `session/load` 原样恢复全部上下文）。回退用的 `_meta` 与技能隔离注入的
   `_meta.claudeCode.options` 按层深合并，避免互相顶掉。
3. **转录标记**（`_acpp/retry`）。重试时往 acpp 自己的转录里追加一行
   `{"dir":"local","msg":{"method":"_acpp/retry","params":{"fromTS":…}}}`，
   重建时把 `fromTS` 那条 prompt 起、到标记为止的内容整段丢弃。
   记时间戳而不是行号：转录读取会跳过写了一半的行，行号与切片下标对不上。

作用域限定在**最后一条用户消息**：从历史中间某条重来会丢弃后面全部对话，
是破坏性操作，需要单独的确认流程，本次不做。

## 代价与降级

- **耦合 claude 的私有存储**。它的转录格式、目录布局、`resumeSessionAt` 语义
  都不是对外契约，升级可能失效。因此所有失败路径都收敛成
  `ErrRewindUnavailable`，调用方据此**降级为原地重发**——回退没了功能不消失，
  只是上下文里留着作废那轮的痕迹。
- **codex 永远走降级**（它根本没有这张对照表）。响应里的 `rewound` 字段
  如实告诉界面这次做到了哪一步。
- 回退后 agent 侧的 sessionId 不变，新内容接着写进同一个 claude 转录、
  `parentUuid` 指向截断点形成分支树（与 Claude Code 的 `/rewind` 同一套机制）。

## 考虑过但没选

- **等协议支持**：`session/fork` 加截断参数是最干净的解，但没有时间表，
  而重复气泡是每次 529 都会撞上的问题。
- **自己重建上下文**（开新会话，把截断后的历史重新喂一遍）：token 成本翻倍，
  且工具调用的结果无法重放，agent 会以为那些活没干过。
- **只做重发、不碰上下文**：两端行为一致、实现最简，但失败轮的痕迹留在上下文里，
  claude 侧能做得更好却不做，说不过去。

## 验证

`probe_resume_at.py` / `probe_resume_uuid.py`（一次性探针，未入库）实测：
同一会话塞两个暗号，用第一轮 assistant 的 uuid 做 `resumeSessionAt` 重开，
提问只答出第一个暗号；对照组（只 `resume` 不截断）两个都答得出。
端到端复核见会话 106：重试后消息列表无重复，claude 转录里两条 user 消息
并列挂在同一个 `parentUuid` 下。
