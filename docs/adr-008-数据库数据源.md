# ADR-008：数据库数据源（MySQL）

日期：2026-08-17　状态：已采纳（会话侧的租户限制已被 [adr-010](adr-010-租户会话能力与-owner-对齐.md) 推翻：租户与 owner 同一项目过滤规则）

## 背景

会话里干的活经常绕不开数据库：查一眼表结构、跑个统计、确认某条数据是不是脏的。此前只能让 agent 在终端里敲 `mysql` 客户端——凭证得写在命令行里、结果是一坨等宽文本、跳板机后面的库根本连不上。

用户诉求四条：SSH 隧道连 MySQL、斜杠命令查看有哪些库、AI 能读库表并执行语句、支持多段语句执行；接入方式指定为 MCP。

## 产品形态（用户拍板）

| 维度 | 决策 |
| --- | --- |
| 连接身份 | **项目 + 环境**两级（`pp-game` 的 `local` / `dev` / `pre`），不是自由命名的连接 |
| 可见范围 | **会话只能看见自己所在项目的数据源**，AI 与斜杠命令都一样 |
| 配置入口 | 侧边栏独立的「数据库」菜单（owner 专属） |
| 连接生命周期 | MCP 调用**一次性连接**，用完关闭，不留连接池 |
| SQL 权限 | **全放开**，靠数据库账号管（要只读就配只读账号），软件层不做语句白名单 |
| 斜杠命令 | `/db` 是**本地命令**：前端拦截、结果只给用户看，不进对话、不耗 token |
| 表单形态 | 照 Navicat：常规 / SSH / 高级三个页签，SSH 验证方式是密码/公钥/密码和公钥三选一 |
| 结果护栏 | 最多 1000 行，**在我们这侧截断**——不改写用户 SQL、不在库上设会话变量 |
| 结果展示 | AI 的查询在对话里有专用组件：语句 + 字段 + 可滚动数据 |

## 决策

### 1. 项目是可见性边界，执行点只有一个

数据源里躺着生产库凭证。一条开在 A 项目的会话（尤其是 AI）能列出 B 项目的连接，就等于把所有项目的库摊在同一张桌子上——迟早有人在错的库上跑对的语句。

所以过滤不做在界面层，做在**取数据源的那一步**：`datasource.Service.ForCwd(ctx, cwd, onlyEnabled)`。MCP 工具面、会话侧 REST 端点走的都是它，绕不过去。项目从会话 cwd 推导（工作区根下的相对路径与仓库名都算候选，worktree 归主仓库，工作区之外用最近的 git 仓库目录名）。

**推不出项目就一个都看不见**，不是「看见全部」。宁可让用户去项目目录里开会话，也不要留一个「在家目录随便聊聊就能连生产库」的口子。

### 2. 连接一次性，不做连接池

每次调用现拨现关，SSH 隧道随连接一起来去。连接池要处理探活、重连、并发争用与跨环境串号，而一个数据库面板的调用频率根本不值得付这份复杂度。

SSH 隧道不走本地端口转发，而是给 mysql 驱动注册一个自定义网络名（`acpp-ssh`），把每条隧道的去向放进一张表用 DSN 的 addr 索引——少一次本地 TCP 跳转，也不占端口。驱动的 dialer 注册表是全局且不可注销的，所以只注册这一个名字。

跳板机指纹按 `~/.ssh/known_hosts` 校验，**刻意不提供跳过开关**：隧道后面挂的是生产库，`InsecureIgnoreHostKey` 等于把中间人攻击的门开着。首次连接的一次性成本换真实的身份校验，错误信息里直接给出 `ssh-keyscan` 补录命令。

### 3. 权限交给数据库，不做语句白名单

用户拍板全放开。这不是偷懒：软件层的语句过滤挡不住真正危险的写法（存储过程、动态 SQL、`/*! */` 版本化注释），却会给人「已经安全了」的错觉，反而让人敢用高权限账号连进来。数据库账号是真正的边界——要只读就配只读账号。

### 4. 护栏全在我们这侧

行数上限 1000（默认 500）。截断不靠给用户的 SQL 自动加 `LIMIT`，也不靠在库上 `SET SESSION MAX_EXECUTION_TIME`——**用户的库我们只读它、不改它的行为**，改写 SQL 更是会让人对着结果怀疑到底跑了什么。

做法是用流式游标（`database/sql` 的 `rows.Next()` 逐行读，不是 GORM 那种一次性物化），读满上限就取消这次查询的 context，驱动会真的断开而不是把剩下的几百万行读完再丢掉。

**诚实的边界**：断开之后，正在往回传结果的查询会因写失败很快中止；但还在扫描/排序、尚未开始吐数据的查询，MySQL 不会察觉客户端已走，会继续跑完那一段。要立刻杀掉必须发 `KILL QUERY`，那是在库上动手，不在本决策的范围里。

### 5. 多段语句自己切分，逐条执行

不用驱动的 `multiStatements`：那样只能拿到一个合并结果，哪条失败、哪条改了多少行全看不见。自己切分（处理引号、三种注释、`DELIMITER`）后逐条执行，每条有独立的耗时、影响行数与错误定位，遇错即停（与 mysql 客户端默认行为一致），前面成功的结果照常返回。全部语句共用同一条物理连接，事务、临时表、会话变量跨语句有效。

### 6. 工具输出用制表符分隔，因为它要被解析两次

MCP 的 content 是纯文本，模型读到的就是那段字符串。用制表符分隔的表格而不是 JSON：token 只有一半，列名不必每行重复。

但它还有第二个读者——前端要把 AI 的这次查询渲染成**真正的表格组件**（ACP 的 tool_call 不透传结构化内容，只剩文本）。制表符格式因此成了两端共同的约定：后端 `datasource/render.go` 产出，前端 `lib/db-result.ts` 解析回结构化，再交给与 SQL 控制台**同一个** `SqlResultView` 渲染。改任何一侧都要同步另一侧；解析失败退回原始文本，不编造表格。

### 7. MCP 协议外壳提为叶子包

编排（adr-006）已经有一套 MCP server，数据库是第二套。JSON-RPC 信封、工具声明与分发抽成 `internal/mcp`，业务包只负责「这次调用有哪些工具、工具怎么执行」。多一个挂给 agent 的能力面，不该多抄一遍协议。

### 8. 挂载是有条件的，两端注入口不同

会话所在项目没有可用数据源时**什么都不挂**：工具清单里凭空多出五个用不了的 `db_*` 只会让模型乱试，也白占它的注意力。

- **claude**：MCP 走 `_meta.claudeCode.options.mcpServers`，同时把工具名写进 `allowedTools` 预批——数据库工具一次会话要调好几轮，每轮弹权限卡没有意义（权限边界已经交给数据库账号了）。另附一段系统提示，列出本项目有哪些数据源，并要求写 SQL 前先看表结构。
- **codex**：走 `session/new` 的 `mcpServers`。不能写进 config.toml——那里定义的 http MCP 是懒连接，启动不 `tools/list`，模型工具清单里看不到（adr-006 踩过）。

## 影响

- 新增 `internal/datasource`（业务）与 `internal/mcp`（叶子）两个包；`orch/mcp.go` 改为复用后者，行为不变。
- `Session` 加 `mcpToken`（懒生成，不出 API）；`sessions` 表新增一列。
- 新增 `/api/datasources/*`（owner 专属）、`/api/sessions/{id}/datasources*`（项目过滤）、`/api/mcp/db/{token}`（agent 回连）。
- 前端新增 `/databases` 页与 `components/db/`；`types/acp.ts` 与 locales 因行数硬线按域拆出 `types/db.ts` 与 `locales/{zh,en}-db.ts`。

## 尚未做

- 只支持 MySQL。PostgreSQL 等按同一套形状扩展即可（连接层换驱动、schema 查询换语句），但没有需求前不预建抽象。
- 查询结果不能导出文件；要导出先在 SQL 控制台跑完再复制。
- 密码明文存在本地 SQLite 里（与租户 token 同一档待遇）。这是本机工具的既有姿态，真要改得先有一套主密钥方案。
