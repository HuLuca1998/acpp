# ADR-012：编排与角色下线——外化子代理这条路走不通，整块删掉

日期：2026-08-20 ｜ 状态：已实施

推翻 [adr-006（编排——把 agent 的子代理外化为可观察的真实会话）](adr-006-编排-外化子代理.md)。adr-006 的实测结论仍然成立，被推翻的是产品判断，不是协议事实。

## 背景

编排（adr-006）把 agent 内部的子代理外化成真实 ACP 子会话：主控会话挂我方 MCP server，
需要帮手时 `hire_role(role, task)` 拉起一条按角色注入人格的子会话，同步跑完再把结论还给主控。
角色（Role）是这套调度的雇佣目录，只为编排存在。

真机用下来效果不尽如人意：主控的调度判断不稳，派活的粒度与时机常常不如让人直接开一条会话；
同步 spawn 把一条主会话的时间线钉死在子任务上，中途只能急停；角色预设（persona + 模型/权限档）
带来的差异远小于维护它的成本。**一个用不顺手的功能留在界面上，比没有更糟**——它占着导航、
分走注意力、每次改会话链路都要多考虑一条并行的实现。

## 决策

**整块下线，不留降级形态。** 编排与角色的页面、API、数据模型、服务全部删除；
不保留「隐藏入口」「实验开关」这类半死状态——留着就还得维护。

对会话功能**零影响**是这次清理的硬约束：编排从一开始就是与普通会话分表、分路由、分服务的
（adr-006 的隔离契约就写了「编排整体可删而不影响普通会话」），这次正好兑现它。

删除范围：

- 前端：`routes/orchestrator*.tsx`、`routes/roles.tsx`、`components/orchestrator/`、`components/roles/`、
  `hooks/use-orch-chat.ts`、`hooks/use-task-chat.ts`、`lib/api.ts` 的 `roles`/`orchestrator` 两组端点、
  `types/acp.ts` 的 `Role`/`RoleInput`/`OrchSession`/`OrchTask`、导航项与 i18n 词条。
- 后端：`internal/orch/` 整包、`httpapi/orch.go`、`httpapi/role.go`、`model/orch.go`、`model/role.go`、
  `/api/roles*` 与 `/api/orchestrator/*` 全部路由（含编排专属的工作区/终端/数据源转发与 `/api/mcp/{token}`）。
- 顺带回收的编排专属物：`stream.Event.Task`（`task_update` 事件）、终端分组的 `keyOffset`（只为编排错开 id 空间）、
  `acp.EnsureCodexHome`（导出 wrapper 只供编排/角色搭专属 CODEX_HOME，包内技能隔离用的私有实现保留）、
  `acp.OpenOptions.ExtraEnv`（唯一使用者是编排）。

保留：`internal/mcp`（协议外壳，数据库工具面在用）、`internal/stream`（会话 SSE 在用）、
`/api/mcp/db/{token}`（数据库 MCP 端点）、`acp.OpenOptions.MetaExtra` / `MCPServers`（会话侧挂数据库工具在用）。

## 遗留数据

`roles` / `orch_sessions` / `orch_tasks` 三张表**不 DROP**，只从 `AutoMigrate` 列表移除——
与 messages 表退役（adr-003）同一处理：代码不再认识它们，旧库里的数据留在原地不动。
删表要写迁移、要考虑回滚，而这三张表既不占用运行时资源也不参与任何查询，删它的收益是零。
编排会话的转录 JSONL 同理留在转录目录里，随会话记录一起被用户自行清理。

## 后果

- 导航从八项收到六项，会话与技能重新成为主线，界面里不再有「另一种会话」。
- 多代理协作的需求回到 agent 自己的子代理机制（claude 的 Task 工具）——它对用户是黑盒，
  但黑盒里的过程我们已经能看见了（adr-009 子代理转录 + `tool_call` 的 `isSubagent`/`subagentOf` 字段），
  这条路的可观察性比 adr-006 落地时好得多，这也是下线成本变低的原因之一。
- 若将来重做多代理，起点是 adr-006 的实测依据（MCP 挂载、同步 spawn 超时、两端注入口差异）
  与本文的失败原因，不是这次删掉的实现。
