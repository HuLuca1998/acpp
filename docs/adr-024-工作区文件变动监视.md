# ADR-024：工作区文件变动监视

日期：2026-09-16　状态：已采纳

## 背景

工作区面板（文件树、查看器、git 面板群）此前只有一条重读的触发路径：**agent 干完一件事**——轮内每完成一次工具调用合帧刷一次（1.5s 窗口），外加 turn 结束刷一次。

这条路径覆盖不了两类情况，而它们恰恰是用户抱怨的来源：

1. **改动不来自 agent**。用户自己在编辑器里改的、命令行里跑脚本生成的、另一条会话在同一个目录里干的活，界面一概不知道，看到的是旧内容。
2. **查看器根本没接上这条路径**。它既没有刷新按钮，也没订阅刷新广播——打开一个文件之后，它显示的就是打开那一刻的快照，直到用户换个文件再换回来。

第 2 条是缺口，补上订阅即可。第 1 条要一条新的信号源：文件系统本身。

## 决策

1. **三条互补的重读路径，每条都有手动刷新兜底**：
   - agent 干完一件事（原有）——它管得到版本库的动静，`commit` 只改 `.git`，文件系统那边看不见；
   - 文件真的变了（本 ADR）——管得到 agent 之外的人；
   - 每个面板头部的手动刷新按钮（`PanelRefreshButton`，全局一个样）。
2. **后端监视，SSE 推送，事件只有一种**。新端点 `GET /api/sessions/{id}/fs/watch`（草稿态 `/api/workspace/fs/watch?cwd=`），推 `{kind:"fs_changed"}`，**不带路径**——面板本来就要整片重读（文件树、git 汇总、正在看的那个文件），逐条路径对它们没用，反而要多维护一份状态。
3. **两级防抖**：后端把成串事件合帧成一声（400ms 窗口，安静下来才发），前端再限最小间隔 1s。一次构建、一次 `git checkout` 在文件系统那边是几千个事件，界面要的是「这阵子过去之后重读一遍」。
4. **按目录共用监视器**（`fswatch.Hub`）：同一个工作目录被几个页面同时看着（两个标签页、桌面壳加一个局域网访客）只监视一遍，最后一个订阅者离开即收摊。
5. **两条自我克制**：页面进后台就断开连接（没人看的标签页没理由占着长连接，更没理由让后端为它守着一棵树）；后端说监视不了就不再重连（`{kind:"unavailable"}`），退回手动刷新。

## 选型：为什么不是 fsnotify

第一版用了 fsnotify（Go 生态的事实标准），**在真实工作目录上当场不可用**。

fsnotify 在 macOS 上走 kqueue：**一个目录一个文件句柄，而且目录里的每个文件也要一个**（它得靠这个模拟 inotify 的语义）。实测用户的一个工作区根目录，排除 `.git`/`node_modules`/产物之后仍有 **1.3 万个目录、7 万个文件**——光是建立监视就要打开八万多个句柄，耗时与开销都不能接受。加目录数上限只是把「不可用」换成「大目录一律不监视」，而大目录恰恰是最需要它的。

改用 **rjeczalik/notify**：darwin 上走 FSEvents，整棵树一个流，与规模无关；linux 走 inotify，windows 走 ReadDirectoryChangesW。代价有两条，都认：

- 引入 cgo（FSEvents 绑定）。本项目只在本机构建本机架构（`scripts/build-macos-app.sh` 不交叉编译），不受影响。
- 递归流没有「不进这个目录」的开关，排除只能在**事件这一侧**按路径做。因此 `.git`/`node_modules` 一类目录的动静仍会送到进程里，只是被丢掉——白跑一趟，但不触发刷新。

## 边界与代价

- **`.git` 不监视**，所以 `commit`、`fetch` 这类只动版本库的操作不触发刷新；那部分由 agent 广播与手动刷新覆盖。反过来 `checkout` 会改工作区文件，照常触发。
- **根目录自身的事件被丢掉**。FSEvents 把「某个子项变了」也报到父目录头上，于是 `.git/index` 写一次，根目录跟着来一条——只看排除名单的话被挡掉的动静会从这条绕回来，每跑一条 git 命令界面就空转一次。真有文件动了，它自己那条路径的事件一定会来，所以丢掉不会漏报。
- **事件缓冲满了就丢**（256）。我们只要知道「有动静」，丢掉的那些不改变结论。
- **监视建不起来不是故障**：目录不存在、平台配额用尽，一律回 `unavailable`，界面退回原有的两条路径。
