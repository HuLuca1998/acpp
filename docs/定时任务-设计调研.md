# 定时任务设计调研（Discord 定时报告与巡检）

> 状态：**已落地**（2026-09-03，决策记录见 [adr-020](adr-020-discord-定时任务.md)，实现与本篇的出入也记在那里）。
> 本篇保留为 openclaw 的源码级分析与方案推导过程；系统现在是什么样以 README「定时任务」一节为准。
> 日期：2026-09-03

## 0. 一句话结论

定时任务挂在 **Discord 频道绑定**上：一条任务 =「频道 + cron 表达式 + 一段自包含的任务提示词」。
到点时 bot 在频道里发一条起始消息、以它开一个子区、在**全新 acp 会话**里跑这段提示词；
成果（报告卡 / 文件 / 正文）落在子区里，起始消息编辑成一行状态与摘要；跑完子区可以接着聊。
调度器是进程内的一个 goroutine，任务与运行记录存 `discord.json`。AI 在对话里通过 `acpp-cron`
工具面自己建任务（投递固定为当前频道），`scheduled-task` 技能教它把任务提示词写成无人值守也能跑的样子。

这与 openclaw 的模型同构（isolated session + announce 直投 + agent 自建任务），但省掉了它的
main session / heartbeat 那一整层——acpp 没有「常驻主会话」这个概念，也不需要。

## 1. openclaw 是怎么做的

读的是 openclaw 主干源码（`src/cron/`、`src/agents/tools/cron-tool*.ts`、
`packages/gateway-protocol/src/schema/cron.ts`）与官方文档，不是二手教程。

### 1.1 模型

| 维度 | openclaw 的做法 |
| --- | --- |
| 任务在哪跑 | Gateway 进程内的调度器（不在模型里）。Gateway 不在线任务就不触发 |
| 存储 | 任务与运行历史存 SQLite（早期是 `~/.openclaw/cron/jobs.json` + `runs/*.jsonl`） |
| schedule | `at`（一次性 ISO 时间）/ `every`（毫秒间隔）/ `cron`（5 段表达式 + IANA tz，**按 tz 的墙钟解释，绝不预转 UTC**）/ `stream`、`on-exit`（进程事件驱动） |
| sessionTarget | `main`（主会话，注入 systemEvent 等心跳消费）/ `isolated`（全新会话 `cron:<jobId>`）/ `current`（挂回创建它的那条对话）/ `session:<key>` |
| payload | `systemEvent`（文本进主会话，不跑模型）/ `agentTurn`（跑一轮模型，可覆盖 model / thinking / timeoutSeconds / toolsAllow）/ `command`（纯 shell）/ `script` |
| delivery | `none` / `announce`（**调度器直接经渠道适配器发出最终回复**，不再拉起主 agent 转述）/ `webhook`。announce 带 `channel` + `to` + `threadId` |
| 无人值守契约 | 任务的 `message` 就是那一轮的**全部上下文**（"self-contained"）；最终回复必须是成品不是计划；没事汇报回 `NO_REPLY`，调度器识别后**压掉投递** |
| 并发 | 同一任务上一轮没跑完，本轮记 `skipped`（`runningAtMs` 标记做准入） |
| 失败 | 连续失败退避 30s→60s→5m→15m→60m；连续 10 次自动停用；连续 2 次失败后向任务的 announce 目标发告警（1h 冷却） |
| 超时 | isolated agentTurn 默认 60 分钟看门狗 |
| 重启 | 过期的 isolated 任务**重新排期而不是立刻补跑**（避免启动窗口里挤一堆模型调用）；`skipMissedJobs` 可配 |
| 整点错峰 | 分钟为 0 的 cron 默认随机延后最多 5 分钟 |
| agent 自建任务 | 内置 `automations` 工具（原名 cron）：`status/list/get/add/update/remove/run/runs/next_check/wake`。**从对话里建任务时 delivery 缺省 = 当前对话所在渠道**（`resolveCronCreationDelivery` 从当前 delivery context 推）；agent 建的任务**继承创建那一轮的工具策略、不能放宽** |
| 心跳 | 与 cron 平行的另一套：主会话每 30 分钟醒一次读 HEARTBEAT 清单，没事回 `NO_REPLY`。文档明说「周期性任务用 automations，不要写进心跳」 |

给模型看的工具描述有几句值得原样记住（`buildCronToolDescription`）：

- "Never exec sleep/poll as timer."——别让模型用 sleep 循环冒充定时器。
- "18:00 Shanghai => {expr:\"0 18 * * *\", tz:\"Asia/Shanghai\"}"——用一个例子钉死时区语义。
- "message is that run's entire context — self-contained."——任务提示词必须自包含。
- "Fire on failures/timeouts too; success-only watchers look healthy when broken."——巡检类任务出错也要发声。

### 1.2 值得抄的与不必抄的

**抄**：isolated 会话 + 调度器直投；自包含提示词契约与 `NO_REPLY` 静默约定；同任务不重入；
失败退避 + 自动停用 + 告警发回投递目标；重启不补跑；agent 建任务默认投递到当前对话；cron 表达式带显式 tz。

**不抄**：main session / systemEvent / heartbeat / wake 那一层（acpp 没有常驻主会话，Discord 子区各自独立）；
`command` / `script` / `stream` / 条件触发脚本（那是把 openclaw 做成通用自动化平台，我们的任务只有一种形态
——「跑一轮 agent」，要跑脚本让 agent 去跑）；webhook 投递（没有消费者）；pacing 自适应节奏（v2 再看）。

## 2. acpp 已有的积木

定时任务在 acpp 上是**组装题**，不是新造：

| 需要什么 | 已经有什么 |
| --- | --- |
| 任务的执行环境（工作目录 / 模型 / 权限档 / 库 / 机器） | `discord.Binding`：频道绑定就是一份完整的环境定义（adr-016/018/019） |
| 一次运行的会话 | 子区对话管线 `runTurn` → `acpMgr.Prompt`：独立会话池（4 席 / 30 分钟轮超时 / 20 分钟空闲回收），`session/load` 恢复 |
| 工具面 | `Deps.Mounts` 按子区 key 挂 acpp-db（锁到绑定的库）/ acpp-server（锁到绑定的机器）/ acpp-report / acpp-chat（send_file） |
| 成果交付 | 报告卡 + gist 外链 + 整页长图（`reportOpened`）、`send_file` 三形态、正文分段发送 + markdown 转译 |
| 权限 / 提问 | 按钮裁决卡、一次性表单，卡片 @ 发起人 |
| 场景提示词注入 | `OpenOptions.InstructionsExtra`（claude 生效）+ `discordInstructionsFor(b)` |
| 技能 | html-report / db-query / send-file 已在库里；server-inspect 有范本 |
| 后台循环范例 | `reapIdle`、`startLinkCleanup`（ticker + ctx） |
| 存储 | `discord.json` 原子写（`store.update`） |
| 管理面 | 网页 Discord 页 + `/api/discord/*`；斜杠命令表 `slashCommands` |

缺的只有四样：**调度器**、**任务与运行记录的数据模型**、**「没有人发消息」时怎么起一个子区并跑一轮**、
**agent 自建任务的工具面 + 教它怎么写任务的技能**。

## 3. 设计

### 3.1 形态：任务属于频道，一次运行 = 起始消息 + 子区 + 全新会话

```
频道 #ppgame-prod（绑定：pp-game@prod · claude · auto-edit · 库 pp-game/prod · 机器 dmit-prod）
│
├─ 📅 用户七日行为日报 · 09-03 10:00 · ✅ 4分12秒 · 🔧 15 · DAU 12.3k ↓2% …   ← 起始消息（状态 + 一行摘要）
│    └─ 子区「用户七日行为日报 · 09-03」                                      ← 运行过程与成果都在这
│         ├─ 📋 计划卡 / 🔧 工具卡（与普通子区完全一样）
│         ├─ 正文（结论、要点）
│         ├─ 📊 报告卡（gist 外链 + 整页长图）
│         └─ 用户：「留存为什么掉了？」 → agent 接着答                           ← 子区可续聊
│
└─ 📅 日志巡检 · 09-03 12:00 · ✅ 无需汇报                                     ← NO_REPORT：只留一行，子区归档
```

为什么这样而不是「直接往频道发一条报告」：

- **复用率最高**。起始消息扮演的就是普通对话里用户那条 `@acpp`，往下全是现成管线：工具卡、权限卡、
  报告卡、send_file、回合小结、`/stop`、`/usage` 一个都不用改。
- **可续聊**。openclaw 的 isolated 会话跑完就丢，用户想追问得重头来；这里子区 ↔ acpSessionId 照旧落盘，
  追问就是普通子区对话（工具面、库、机器全在）。这是 acpp 比 openclaw 多出来的一条。
- **频道干净**。频道里每次运行只多一行（adr-017 的「主频道只见子区标题」），过程噪音全在子区里；
  巡检无事时连子区都归档掉。
- **人能插手**。跑到一半要授权，卡片出现在子区并 @ 任务创建者，手机上点一下就放行——无人值守但不是无人能管。

### 3.2 数据模型

存在 `discord.json`（沿 adr-016：单文件、回退 = 删文件；量级是每频道个位数任务）：

```jsonc
"jobs": [{
  "id": "j_8f3a…",                    // 随机短 id，对话与命令里引用
  "channelId": "1544537715427516588",
  "name": "用户七日行为日报",
  "schedule": { "cron": "0 10 * * *", "tz": "Asia/Shanghai" },   // 或 { "at": "2026-09-04T09:00:00+08:00" } 一次性
  "prompt": "……自包含的任务提示词……",
  "enabled": true,
  "createdBy": "<discord user id>",   // 权限卡 @ 谁、失败通知 @ 谁
  "createdAt": "…", "updatedAt": "…",
  "lastRunAt": "…", "lastStatus": "ok",
  "failStreak": 0,
  "runs": [                           // 最近 30 次，够 /cron runs 与网页看
    { "startedAt": "…", "endedAt": "…", "status": "ok|error|skipped|silent",
      "threadId": "…", "tools": 15, "tokens": 183000, "summary": "…", "error": "" }
  ]
}]
```

刻意不存的：模型 / 思考深度 / 权限档 / 库 / 机器——**全部跟随频道绑定**，运行时现读。
任务只回答「什么时候、干什么」，「用什么环境」是频道的事，两处存等于两处漂移。

`schedule` 只做 `cron`（5 段 + tz）与 `at`（一次性，跑成功即删）。`every` 用 `*/30 * * * *` 能表达，
不另开一种。tz 建任务时显式落盘（默认取主机时区），显示与解释都不再有歧义。

### 3.3 调度器

- **一个 goroutine，按分钟对齐 tick**（`time.Until(下一整分)`），每次扫描全部启用任务，`next <= now` 的起跑。
  cron 解析用 `robfig/cron/v3` 的 **parser**（只用它算 `Next`，不用它的 runner——循环、并发、失败策略要自己管）。
  成熟依赖，MIT，解析器多年未变。
- **同任务不重入**：上一轮还在跑，本轮记 `skipped`（openclaw 同款）。
- **池满推迟**：discord 会话池 4 席是与人共用的；`acpMgr.Open` 报「too many open sessions」时不算失败，
  1 分钟后重试，最多 10 次再记失败。
- **失败退避与自动停用**：连续失败第 1/2/3 次分别推迟 5/15/60 分钟重跑；连续 5 次自动停用，
  频道里发一条 @createdBy 的通知（「已自动停用，`/cron resume` 恢复」）。数字比 openclaw 的 10 次保守
  ——我们一次运行是一整条 claude 会话，比它贵。
- **重启不补跑**：启动时每个任务从 `now` 重算 `next`；错过的写日志。启动时发现 `runs` 末尾还是
  `running` 的记录，改成 `error: 进程重启中断`。
- **整点错峰**：不做。用户就几条任务，10:00 就是 10:00；错开反而显得不准时。
- **轮超时**：沿用池的 30 分钟；超时即失败。

### 3.4 运行管线：复用 runTurn，加一层「无人值守契约」

一次运行 = `runJob(job)`：

1. 频道里发起始消息 `📅 <名> · 09-03 10:00 · 🔄 运行中`，用它 `POST /messages/{id}/threads` 开子区
   （与 `startThread` 同一条 REST），子区记录落盘（`Thread.JobID` 标记来源）。
2. 组装输入块：**系统注入的前言** + 任务 `prompt`。前言是运行时事实，agent 不知道也推不出来：

   ```
   （定时任务·系统注入）任务「用户七日行为日报」按计划于 2026-09-03 10:00 (Asia/Shanghai) 运行。
   上次运行：2026-09-02 10:00，结果 ok，摘要：「DAU 12.3k ↓2%，新增付费 …」。
   本次运行无人值守，按下面的约定执行：……
   ```

   「上次运行」这一行对巡检类任务是刚需——「只看自上次以来的新增日志」没有它就没法定时间窗。
3. 走 `runTurn` 现有逻辑（挂载、拨设置、typing、Prompt、分段发、回合小结）。
4. 收尾：把回复首段（去掉标题与 emoji，≤200 字）写回起始消息当摘要，状态改 ✅/❌；写 `runs` 记录。
   回复正文恰好是 `NO_REPORT` → 状态 `silent`，起始消息改成 `✅ 无需汇报`，子区归档
   （不删：留痕，偶尔人想看它为什么判定无事）。

**无人值守契约**通过 `InstructionsExtra` 追加（拼在 `discordInstructionsFor` 之后，只有定时运行的会话有）：

- 没有人在线：**不要提问**（elicitation 一律不发；拿不准就按最保守的口径做并在结论里注明假设）。
- 最终回复必须是**成品**（结论 + 报告），不是计划、不是「我将……」。
- 避开需要人工审批的操作：写文件用 Write/Edit，图表手写 SVG，不跑脚本；只读工具面
  （db / server / report / chat）都是预批的，优先用它们。
- 巡检类：**没有值得说的就只回 `NO_REPORT`**；但工具报错、连不上机器、查询超时这类**失败要如实汇报**，不算「无事」。
- 数据从工具里来，没查到的数字不写。

权限请求仍会发生（auto-edit 档下的 bash）：卡片照常发在子区并 @ `createdBy`；没人点，30 分钟轮超时后
这一轮记失败，原因写「等待授权超时」。提问（elicitation）到达时后端直接以「无人值守」拒绝（不发表单），
比留一张没人填的表干净。

### 3.5 入口：三条路，AI 对话是主路

| 入口 | 用途 | 形态 |
| --- | --- | --- |
| **子区里对 AI 说** | 用户的两个场景都是这样发生的：先让 AI 做一次，满意了说「以后每天早上 10 点这样出一份发到这个频道」 | `acpp-cron` 工具面（§4） |
| `/cron` | 手机上看与管：`list` / `run <id>` / `pause` / `resume` / `remove` | 一条命令 + `action` choices + `id`（choices 由当前任务清单动态注入，照 `/server` 的做法） |
| 网页 Discord 页 | 每个绑定下一节「定时任务」：清单（名 / 时间 / 下次 / 上次状态 / 开关）、立即运行、删除、运行记录；表单建任务（名 / cron / 提示词） | `GET/POST /api/discord/jobs`、`PUT/DELETE /api/discord/jobs/{id}`、`POST /api/discord/jobs/{id}/run` |

三处共享同一份服务方法（`AddJob / UpdateJob / RemoveJob / RunJob / Jobs`），
命令表的 `desc` 仍是命令说明的唯一事实源（包规范）。

## 4. MCP 与 skill 怎么分工

沿用 adr-019 定下的三层：**MCP 是原语，skill 是方法论，项目代码 / 工具面是事实源**。定时任务这件事里
还有第三个角色——任务提示词本身，它是「AI 写给未来的、没有记忆的自己的一封信」。

### 4.1 `acpp-cron` 工具面（原语）

挂在子区会话上，与 acpp-chat 共用同一条回连端点与同一枚凭证（token → 子区 → 绑定 → 频道），
server 名单列 `acpp-cron`（工具台按 server 分组，模型也看得清楚）。四个工具：

| 工具 | 参数 | 说明 |
| --- | --- | --- |
| `cron_add` | `name`、`cron`（5 段）或 `at`、`tz?`、`prompt` | 建任务，**投递目标固定为当前频道**（openclaw 的 `resolveCronCreationDelivery` 同款：从凭证推频道，不让模型填 channel id）。返回任务 id + 下次运行时间；同时子区里发一张任务卡（名 / 时间 / 下次 / ▶️ 立即运行 / ⏸ 停用 / 🗑 删除） |
| `cron_list` | — | 本频道的任务：id / 名 / 时间 / 启用 / 下次 / 上次状态 |
| `cron_update` | `id` + 任意可改字段 | 改时间、改提示词、启停 |
| `cron_remove` | `id` | 删 |

不给 `cron_run`：用户想立即跑，说一句「先跑一次看看」——agent 在当前子区直接做就行，那正是
「先做一次再固化」的流程；卡片上的 ▶️ 是给人按的。

工具描述（写给模型看）要交代四件事——adr-019 说过，工具清单是模型每一步都会扫的，比技能更容易被想起来：

1. **触发词**：用户说「每天 / 每周一 / 每隔 / 以后定时 / 到点 / 提醒我 / 固定时间发」——建任务，不要用 sleep 循环冒充。
2. **时区语义**：`cron` 按 `tz` 的墙钟解释，默认主机时区；例子「每天早上 10 点 → `0 10 * * *`」。
3. **自包含契约**（最重要的一句）：任务到点在**全新会话**里跑，**没有这次对话的任何记忆**——数据来源
   （哪个库哪些表 / 哪台机器哪些日志路径）、口径（时间窗、指标定义、过滤条件）、报告结构、交付形态
   （report_open / send_file 的 as）、静默条件，全部写进 `prompt`；不要写「像刚才那样」「同上」。
4. **写完复述**：建完把「什么时候、干什么、发到哪、多久一次」用一句话复述给用户确认，任务卡上有按钮可改。

长配方（几十行 SQL、日志路径清单）可以落成工作目录里的文件再在 prompt 里引用——放
`<workdir>/.acpp-cron/<jobId>/`，与 `.acpp-uploads/` 一样登进 `.git/info/exclude`，不脏仓库；
工作树是持久的，下次运行读得到。

### 4.2 `scheduled-task` 技能（方法论）

工具解决「会不会想起来建」，技能解决「建出来的任务能不能跑好」。骨架：

1. **先做一次，再固化**。任务提示词不是凭空写的：先在当前子区把报告做出来、跟用户对齐口径，然后把
   「刚才实际走过的步骤」写成提示词——查了哪些表、用了什么 WHERE、报告分几节、交付用了什么形态。
   跳过这一步写出来的任务多半第一次就跑歪。
2. **写给一个没有记忆的自己**：提示词要能让一个刚打开的会话不问任何问题就干完。检查清单：数据来源 ✔
   时间窗（相对「运行时刻」表述，如「过去 7 天」）✔ 指标口径 ✔ 输出结构 ✔ 交付形态 ✔ 静默条件 ✔ 失败时怎么说 ✔。
3. **点名要用的技能与工具**：「按 db-query 技能查库」「按 html-report 出报告并 report_open」
   「按 server-inspect 看日志」——技能在每条会话里都注入了，提示词点一下名就是触发器。
4. **巡检类的写法**：只看自上次以来的窗口（前言里有上次运行时间）；分级（错误 / 警告 / 提示），
   只有错误级才值得发；没事回 `NO_REPORT`；工具失败不是无事。
5. **两个场景的范本**（`references/`）：用户七日行为日报（db-query + html-report）、
   服务器错误日志与慢查询巡检（server-inspect + db-query）。

### 4.3 与既有技能的接力

```
对话里（一次性）                              定时运行（每次）
用户：「分析近七天用户行为」                   前言（时间 / 上次结果 / 契约）
  → db-query 查库                                → 任务 prompt 点名 db-query / html-report / send-file
  → html-report 出报告 → report_open               → 同样的工具面（库与机器都锁在频道绑定上）
  → send_file 交付                               → 报告卡 + 长图 + 文件落在子区
用户：「以后每天 10 点发到这个频道」               起始消息编辑成摘要
  → scheduled-task 技能：把上面沉淀成 prompt
  → acpp-cron.cron_add
```

## 5. 两个场景走一遍

**场景 1：用户七日行为日报**

1. `#ppgame-prod` 里 `@acpp 分析一下最近七天的用户行为`。子区里 agent 按 db-query 查 `pp-game/prod`，
   按 html-report 出报告，report_open → 报告卡 + 长图。
2. 用户看完：「不错，以后每天早上 10 点出一份发到这个频道」。agent 按 scheduled-task 技能把刚才的步骤
   写成提示词（表名、口径、报告结构、`report_open`），调
   `cron_add{name:"用户七日行为日报", cron:"0 10 * * *", tz:"Asia/Shanghai", prompt:…}`。
   子区里出任务卡，agent 复述一句。
3. 次日 10:00：频道里出现起始消息与子区，agent 在新会话里按提示词跑完，报告卡落子区，
   起始消息变成 `✅ 4分12秒 · DAU 12.3k ↓2% …`。
4. 用户在子区里追问「付费下降是哪个渠道」——普通子区对话，库还是那个库。

**场景 2：服务器错误日志与慢查询巡检**

1. 频道绑定已锁 `dmit-prod` 机器与 `pp-game/prod` 库。用户先让 agent 巡检一次：按 server-inspect 从
   compose 推日志路径，`docker_logs since` / `server_grep` 找 ERROR，`db_query` 查慢查询表
   （或 `server_read tail` 慢日志）。
2. 「每两小时巡检一次，有错误再发」→ `cron_add{cron:"0 */2 * * *", prompt:…含「无异常回 NO_REPORT」}`。
3. 每两小时：多数时候起始消息只是 `✅ 无需汇报`，子区归档；出事时子区里是错误摘录 + 慢查询清单 + 建议，
   起始消息带一行 `❌ 3 条 ERROR · 2 条慢查询 >5s`。
4. 机器连不上：agent 按契约如实汇报「无法连接 dmit-prod」，不算无事；连续失败 5 次自动停用并 @ 创建者。

## 6. 边界与风险

- **无人值守的权限面**：任务按频道绑定的权限档跑。`auto-edit` 下写文件自动放行、bash 要批——报告类任务
  按契约不跑脚本，基本不会碰权限卡；`full` 档的频道等于让定时任务无人审批地执行任意命令，这是频道级的
  显式选择，网页与 `/status` 里要看得见「本频道有 N 条定时任务」。**这是闸门不是边界**
  （与 adr-008/019 同一口径）：真正的边界是绑定的库账号与 SSH 账号的权限。
- **任务提示词是持久化的注入面**：谁能建任务谁就能让 agent 每天无人值守地做事。建任务的人只能是频道成员
  （bot 只受邀进自己的服务器，adr-016 的信任模型）与网页 owner；任务卡与 `/cron list` 上永远显示 `createdBy`。
  对外开服务器前这条与 adr-016 的白名单一起补。
- **成本**：一次运行 = 一整条 claude 会话（技能注入 + 工具调用 + 报告）。`runs` 记 token，`/usage` 与网页
  按任务汇总；巡检类靠 `NO_REPORT` 省的是投递不是 token——每两小时一条会话仍然是每两小时一条会话，
  agent 建任务时的复述要带上频率让用户心里有数。
- **Discord 限速**：每次运行 1 条起始消息 + 1 次开子区 + 若干子区消息，与人工对话同量级；巡检归档子区是
  1 次 PATCH。都在正常限速内。
- **时钟**：Mac 睡眠时进程不跑，醒来后按「重启不补跑」处理——错过就错过，下一次照常。桌面版常驻时这是
  最常见的失约原因，任务卡的「上次运行」要让人看得出来漏了。
- **与网页会话侧的关系**：本方案是 Discord 专属，理由是投递面与环境定义都现成；网页侧要定时（比如定时跑测试
  往通知中心发）不在本篇，调度核心提成叶子包（§7 M1）就是给那一天留的口子。

## 8. 待拍板

1. **起始消息要不要带摘要**：方案是「回复首段 ≤200 字」写回起始消息。备选：只写状态一行，摘要全在子区。
   前者频道里一眼能看到关键数字，代价是首段不一定是摘要（技能里要求首段写 TL;DR 可以兜住）。
2. **NO_REPORT 时子区去留**：方案是归档留痕。备选：连起始消息一起删，频道里零痕迹——更干净，
   但「它到底跑没跑」只能去网页看。
3. **一次性任务（`at`）要不要做**：「明早 9 点看一眼部署结果」这类提醒式用法，实现成本几乎为零，
   但会引来「提醒我……」这一大类需求；做的话技能里要划清楚它与报告类的边界。
4. **任务是否跟随绑定的权限档**：方案是跟随（一处口径）。备选：任务级 `access` 快照，建任务时锁定、
   频道后来放宽不影响它——更安全，多一个要解释的字段。
5. **投递到别的频道**：v1 只投当前频道（环境定义在绑定上，投别处的语义不清）。真有「跑在 prod 频道、
   发到 #alerts」的需求再加 `deliverTo`（同 guild 内的频道 id）。
