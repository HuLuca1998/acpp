# ADR-010：租户会话能力与 owner 对齐

日期：2026-08-19　状态：已采纳（部分推翻 [adr-007](adr-007-多租户隔离与项目管理.md) 的数据源租户面）

## 背景

adr-007 把数据库数据源整个划成 owner 专属面：租户请求会话侧数据源清单时直接返回空列表。但实际形状从一开始就不自洽——AI 侧的 MCP 挂载与 @ 引用展开只按工作目录匹配项目、不看身份，租户目录名撞上项目名时，租户会话里的 AI 照样挂上 `db_*` 工具、能查库。界面选不了、AI 却能用，违背了自家原则「界面能看到的范围与 AI 能操作的范围必须是同一个」。

用户拍板：**租户会话的所有功能与 API 与 owner 一致**。

## 决策

- **会话侧能力面不按身份分家**：`/api/sessions/{id}/datasources*` 与草稿态 `/api/workspace/datasources*` 对租户与 owner 同一规则——按工作目录所属项目过滤。MCP 挂载与 @ 引用展开维持原状（本来就不看身份）。
- **管理面照旧 owner 专属**：数据源配置（`/api/datasources*`）、系统面、编排、租户管理不变。凭证永不经会话侧下发（清单只带 `hasPassword` 标志位）。
- **路径隔离不动**：租户仍被钉在自己的 root 内，这是数据隔离的根基，与功能面无关。

## 理由

与 adr-007 对终端的处理同一哲学：会话内的能力面开放并「明确接受其越权面」，真正的权限交给下游管——终端交给 OS，数据库交给数据库账号（要只读就配只读账号，见 adr-008「SQL 权限全放开」）。软件层的隔离负责「看不见别人的东西」，不负责扮演数据库的权限系统。

## 后果

- 租户在自己 root 下的目录名与 owner 配置的项目名同名时，即可看到并使用该项目的数据源。这是**特性不是漏洞**：owner 给租户发邀请时即视为信任其使用配套数据库（配合只读账号可控风险）。
- 回归保护：`tenant_flow_test.go` 的 `TestTenantFlow_SessionDatasourcesSharedByProject`（租户可见按项目过滤的清单、响应不含密码、管理面仍 403）。
