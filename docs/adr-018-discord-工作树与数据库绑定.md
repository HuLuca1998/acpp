# ADR-018：Discord 频道的工作树布局与数据库环境绑定

- 日期：2026-08-31
- 状态：已落地
- 相关：[adr-016 频道工作区](adr-016-discord-频道工作区.md)（本篇修订其磁盘布局）、[adr-017 子区对话](adr-017-discord-子区对话.md)、[adr-008 数据库数据源](adr-008-数据库数据源.md)

## 背景

用户的真实用法是「一个项目 = 一组频道」：`pp-game` 在 Discord 里有 prod /
pre / dev 三个频道，各自对应一套环境。落到 adr-016 的实现上有两个洞：

1. **代码看错分支**。老布局是「一频道一个完整 clone」，落点
   `<根>/<组织>/<仓库>[@<分支>]`——同一分支的两个频道直接共用一个检出，
   一个频道切了分支另一个跟着走。用户的原话是「我在 prod 问问题，然后 AI
   读的 live 分支的代码，导致信息不对等」。
2. **数据库看得见全部环境**。数据源的可见性收在 `ForCwd(cwd)`：由工作目录
   推出项目名，返回**该项目下所有环境**。三个频道推出的项目名都是
   `pp-game`，于是 prod 频道的 AI 也列得出 dev/pre 的连接，`db_query` 想打
   哪个打哪个。

## 决策

### 〇、频道永远工作在自己的分支上

`/init` 选的是 **base**，不是频道要工作的分支。频道的工作分支由系统生成：
`discord/<频道名>`，重名就 `-2`、`-3` 往下排（本地与远端都比对），工作树
目录同理不重名。

理由是提交链的最后一步：`pre` / `prod` / `live` 这类分支基本都有保护规则，
agent 干完活提交推不上去，前面做得再好也白搭。base 只当起点，产出留在自己
的分支上，之后正常发 PR 回 base。

重绑（换模型、换库）时复用上次那条工作分支——每次 `/init` 换一条新分支会
把没推的提交甩在旧树里。换了仓库或换了 base 才重新生成。

建树的三种情形，取舍都在「别弄丢已有的提交」：本地已有这条分支就直接检出
（**不**对齐 origin，上面可能有没推的提交）；本地没有远端有就跟踪远端那条；
都没有才从 `origin/<base>` 切。

### 一、一仓库一份 git 数据，一分支一棵工作树

```
<workRoot>/<组织>/<仓库>/
  ├── .repo/             bare 克隆，唯一一份 git 数据
  └── .worktree/<分支>/   频道的工作目录
```

- **频道的 cwd 永远是一棵单分支工作树**。AI 的 grep/glob 会把工作目录整棵
  扫一遍，目录里躺着别的分支的副本就会答错——所以项目目录只是容器，不是
  工作树。（这也是没有把 `.worktree` 放进一棵正在用的工作树里的原因：那样
  三个分支的副本会同时出现在同一次搜索里，比原来更糟。）
- **bare 而不是普通克隆**：普通克隆的主工作树占着默认分支，绑默认分支的
  频道就建不出工作树（`already checked out`）。bare 没有主工作树，每个分支
  都空闲。
- **fetch refspec 必须改成 `+refs/heads/*:refs/remotes/origin/*`**：
  `clone --bare` 默认把远端分支直接写进本地 `refs/heads/*`，而本地分支正被
  工作树占用，fetch 会被拒。改了之后远端状态落在 `origin/*`，本地分支由各
  棵工作树自己管；建树时若本地分支落后就先 `branch -f` 对齐 origin。
- 目录名由分支唯一决定，绑同一分支的两个频道复用同一棵树（git 本来也不许
  一个分支挂两棵树）。分支名里的 `/` 压成 `-`，`..` 开头的点全部剥掉——
  目录名不许穿越出去。
- **老布局不迁移，但要让路**：`<仓库>@<分支>` 的独立克隆留在磁盘上（里面可能
  有没推送的活），频道重新 `/init` 一次即切到新布局。`datasource` 的项目推断
  同时认 `.worktree/<分支>` 与老的 `@分支` 后缀。
  唯一的冲突是**默认分支**的老克隆：它就落在 `<组织>/<仓库>`，正是新布局的
  项目容器目录，不挪开的话 `.repo` 与 `.worktree` 会长进那棵老工作树里（老
  频道的 AI 一 grep 就扫到别的分支的副本——正是要根治的问题）。因此建树前
  检测到项目目录本身是工作树，就把它整体重命名为 `<仓库>@legacy`，并在
  `/init` 回执里报出新位置。**只重命名不删除**：里面有没推送的活，还有
  `git status` 看不见的 `.gitignore` 文件（上传件、`.env`、构建产物）。

### 二、可见数据源从 cwd 收敛为 Scope

`datasource.Scope{Cwd, Only}` 取代裸 cwd 成为取数入口的参数：

- `Only == 0`：老口径，由 cwd 推项目、返回该项目全部环境。
- `Only > 0`：**锁死到那一条数据源，跳过项目推断**。显式绑定比从路径猜精确
  得多，频道绑定的意义正是免掉那份猜（`@分支` 后缀曾让项目过滤落空、查出
  `rows:0`，排障两次）。
- 锁定的连接被删或被停用时**降级成空**，绝不回退成「整个项目可见」——降级
  方向只能是更少。

八个取数入口（工具集、`db_sources`、`Resolve`、`@` 引用…）全部经
`ForScope`，收敛一处即全线生效：锁定后 `Resolve` 只剩一条候选，AI 连
`source` 参数都不用填，填错也解析不到别的环境。

作用域随 **peer token** 下发（`PeerTokens.Issue(key, cwd, scope)`）。不能按
cwd 区分：两个频道可能绑同一分支（cwd 相同）却锁着不同的库，按 cwd 发凭证
会让它们互相踢掉对方的作用域。datasource 的凭证 key 也从 cwd 改成调用方 key
（子区 key），一区一枚。

### 三、频道侧的入口与展示

- `/init` **在分支之后多一步「选择数据库」**（默认可不选＝不锁定，老频道
  行为不变）；落盘 `DataSourceID` + `DataSourceRef`（`<项目>/<环境>` 展示
  快照，连接被删之后仍说得清原本绑的是谁）。
  它不在 `/init` 表单里，是真机撞出来的硬限制：**modal 最多 5 个组件**，
  第 6 个直接 `400 BASE_TYPE_MAX_LENGTH`（仓库/自定义仓库/模型/深度/权限
  已经占满）。所以数据库与分支一样，走「消息上的下拉 + pending 中途状态」
  那条路；没配数据源就跳过这一步。
- `/db source:<项目/环境>` 事后换绑，`none` 解除锁定。换绑后关掉该频道所有
  子区的 acp 会话——挂载是 `session/new` 的参数，改不了在跑的会话，下一轮
  重开时凭 `acpSessionId` 走 load 恢复上下文。
- 频道主题、`/status`、置顶手册、`/mcps` 与场景提示词统一显示锁定的库
  （`dbLine` 一处口径）。提示词里点名「本频道锁定 X，别的环境这个频道连不
  到」——三个环境频道共用同一套提示词，唯一的区别就是这句。

### 四、`/git`

顺带补一个观察面命令：分支、与远端的领先/落后、**与 base 的差距**（工作
分支多半还没推，没有 upstream，跟 base 比才知道这轮干了多少）、改动文件按
修改/新增/删除/重命名/冲突分类。每类最多列 12 个（Discord 单条 2000 字符，列全反而看不
清）。现读不缓存——agent 随时在改文件。

### 五、解绑与删频道的清理

解绑（`/unbind`）与**频道被删除**（`CHANNEL_DELETE`）走同一套收尾：先关掉
该频道所有子区的 acp 会话（进程占着工作目录，不退出 `git worktree remove`
会被绊住），再删绑定记录，最后处置工作树。

工作树的去留只有一条规则：**有活就留着**。

- 有未提交的改动、有还没合回 base 的提交、读不出状态、算不出与 base 的
  差距——任何一条成立就保留，并在回执里说清留在哪、为什么。
- 两样都没有才连树带分支删掉：那时它就是一份能从 base 随时重建的副本。
  `git worktree remove` 不加 `--force`，让 git 再把一道关。

判定从严是因为两边的代价不对称：误删是几小时的活，留着只是几百兆磁盘。

子区被删（`THREAD_DELETE`）则只收它自己的会话与记录。频道删了不清理的话
会留下指向不存在频道的绑定——后续每一步都在对着空气操作（这个坑在真机
测试里踩过一次）。

## 边界

「只能查自己那个库」由三层保证，本篇只动第一层：

1. 工具面里只有那一条连接（本篇）。
2. 跨库 SQL 被单库闸门挡（`allow.go`，明写 `别的库.表` 拒绝）。
3. 能不能写由数据源的 `ReadOnly` 与**数据库账号的授权范围**定——后者才是
   真正的边界（adr-008 的既有结论，不加第四层）。

## 未做

- 网页管理页还不能改频道锁定的数据库（`BindingPatch` 只覆盖模型/深度/权限
  四个字段，不会误清 `DataSourceID`）。
- 工作目录被手工删掉时绑定记录还在（下次 `/init` 会重建，但在那之前对话会
  失败）。没做启动对账——自动删绑定的风险大于收益。
- 复用已有工作树时不 fetch 也不 pull，频道用久了代码是旧的（建树时会
  fetch）。`/sync`（fetch + 快进）待做。
