# 全栈性能盘点（2026-08）

一次系统性的性能优化记录：先按大区域切（后端 / 前端），再按小区域切（数据层、
传输层、热路径…），逐点量、逐点改。每条都带改前改后的数字，方法与复现命令
写在末尾。

分支 `perf/full-stack-audit`，15 个提交，无行为变更（除一处明确标注的死按钮清理）。

## 一句话结论

| 场景 | 改前 | 改后 |
| --- | --- | --- |
| 首次打开（传输字节） | 2813 KB 裸传 | **270 KB**（分包 + gzip） |
| 打开一条 35MB 转录的会话 | 348 ms | **207 ms** |
| 工作区刷新一次 git（大仓库） | 92 ms | **41 ms** |
| 面板请求的归属闸 | 2~3 次查询 + 2 次磁盘读 | **1 次三列查询** |
| 打字一个字符 | 重渲整个输入区（11 个组件） | **只重渲输入卡** |
| 流式期间每 80ms | 重建整份历史 + 全部附属面板 | **只重建实时区** |

## A 区：后端

### A1 数据层 —— SQLite 开 WAL

`journal_mode` 是默认的 `DELETE`：写一次就独占整个库文件。而一轮对话里会话
元数据在持续写（用量快照、设置快照、状态流转、提问摘要），前端十几个面板同时在读
——读写互斥的结果是面板请求随机排队几十毫秒，且完全看不出原因。

改动（`server/internal/db/db.go`）：

- `journal_mode=WAL` + `synchronous=NORMAL`：读写并行，读永远不被写挡住；提交
  不再等 fsync（丢的是本机会话元数据，对话本身在转录 JSONL 里）。
- `busy_timeout=5000`：写锁被占时等待发生在连接层，安静且可预期。
- `cache_size=-65536`（64MB）、`temp_store=MEMORY`。
- 连接池收成 4 条：SQLite 同时只允许一个写者，池子放开只会让并发写撞
  `SQLITE_BUSY`。
- GORM 关掉逐条默认事务（本项目没有跨表原子写需求）、开启准备语句缓存。

### A2 传输层 —— 文本响应 gzip

前端产物与消息列表 JSON 原本都是裸传。新增 `httpapi.withCompression`：惰性决策，
攒够 1400 字节且类型可压才压。

| 响应 | 裸传 | gzip |
| --- | --- | --- |
| 消息列表（一屏历史） | 56 KB | **13.6 KB** |
| 前端主分片 | 175 KB | **60 KB** |

三条边界原样直通，**压错比不压严重得多**，各有一条契约测试盯着
（`compress_test.go`）：

- **SSE**：压了分片会攒在压缩窗口里，第一个 token 迟到几百毫秒。
- **带 Range 的请求**：日志面板每 2 秒尾随读转录、媒体预览拖进度条，都靠字节
  偏移对齐，压完对不上。
- **WebSocket 升级**：连接要被 Hijack 走，中间不能有缓冲层。

压缩级别用标准默认档而不是 BestSpeed，依据是实测：主分片 69→60 KB 多花 2.5ms
（带 immutable 缓存，一次更新只付一遍），消息列表 14.2→12.8 KB 多花 0.25ms。

### A3 热路径 —— 归属闸只查三列

文件树、预览、git 的十条端点、终端、日志尾随（每 2 秒一次）、消息列表、提问索引
——每一条都要先过归属闸，而它走的是完整的 `Sessions.Get`：Preload agent 多查一次表、
`toView` 里读两次 `.git/HEAD`、租户会话再查一次 tenants。

闸只需要知道「这条会话归不归你、目录在哪」。新增 `service.Guard` 只
`SELECT id, cwd, tenant_id`，404 语义与 `Get` 完全一致（不属于当前身份的会话当作
不存在，见 adr-007）。改完之后全部面板端点稳定在**亚毫秒**：

```
fs/entries      0.22 ms      transcript 尾随  0.14 ms
messages(热)    0.66 ms      outline         0.57 ms
sessions list   0.62 ms      session get     0.58 ms
```

### A4 对话流 —— 重建合流 + 一遍解到位 + 收尾不排队

三处独立的浪费，全在「一轮结束」这一刻集中爆发：

1. **同一份转录被解析两遍**。轮末前端同时拉消息列表与提问索引，转录刚变过、
   两边都缓存未命中。`rebuildAll` 加按会话合流（后来者等在途那次）。
2. **`turn_done` 排在服务端自己那次重建后面**。界面已经说完话了，还要等几百毫秒
   才变回可用。改成先发 `turn_done`，重建挪到后面异步做——前端收到信号后来拉
   消息列表，那条路径与异步这次共用同一次重建。
3. **同一行 JSON 解两遍**：先解成 `transcript.Entry` 把 msg 原样抄出来，再把 msg
   解成 `wireMsg`。`Store` 加 `ReadLines` 逐行给原始字节，重建的读路径一次解到
   最终形状；公开的 `RebuildMessages` 保留，两条路径的等价性有测试盯着。

35MB 转录的会话冷加载：**348 ms → 207 ms**。

另两处顺手：技能计数改「去重先行」（同 id 的 tool_call_update 不再把几 MB 的
rawOutput 整份 JSON 解一遍，解析前先做一次字节扫描）；访客列表的会话数改一次
`GROUP BY`（原来逐个访客查一遍）。

### A5 工作区数据面 —— git 并发扇出

`git/overview` 串行跑七条命令、`git/branches` 串行跑八条，而它们彼此不依赖。
偏偏这两条正是「agent 每干完一件事就要刷一次」的路径。

| 端点 | 改前 | 改后 |
| --- | --- | --- |
| `git/overview` | 92 ms | **41 ms** |
| `git/branches` | 88 ms | **36 ms** |

- **一轮并发发出**（`runGitParallel`）。未推送提交的两种取法（有无 upstream）都
  先跑、事后挑一份——多一个并发进程不占额外墙钟，比先问再跑多一整轮划算。
- **`--no-optional-locks`**：读类命令默认会顺手刷新并回写索引，为此要拿
  `index.lock`——而 agent 就在同一个仓库里干活，它自己的 git 也在抢。面板刷新
  偶发的几百毫秒卡顿就是这么来的。
- **请求合流**（`shareGit`）：同一个 cwd 上并发的只读请求共享一次执行。实测 4 路
  并发的墙钟与 1 路持平。**合流不是缓存**——第二个请求等的是正在跑的那一次，
  拿到的仍是此刻的真实状态，有测试锁住这条语义。

剩下的 41 ms 里 31 ms 是 `git status` 自己（它要 stat 整个工作树），那是地板。

### A6 周边

- 会话列表不再逐行读工作目录的 `.git/HEAD`（50 条 = 一百多次磁盘读）。唯一的
  消费者是侧栏分组里的 `branch` 字段，而那个字段**从来没有人读过**——一并删掉。
  分支现在只在单条会话的视图里现读。

## B 区：前端

### B1 构建分包 —— 首屏 2813 KB → 270 KB

改前是一个 2.4 MB 的单包：打开一条会话要先下载并解析从没打开过的图表库，
开不开终端都先付 330 KB 的 xterm。改成三层：

- **页面按路由 `lazy`**（`App.tsx`）。占位先隐身 200ms 再淡入——本机加载一个分片
  是几毫秒的事，闪一下的 spinner 比空白更像卡顿。
- **xterm 连样式表一起动态 `import`**：330 KB，是整个前端最大的单个依赖，而绝大
  多数会话从头到尾不开终端。
- **大依赖按场景分组固定归属**（react / xterm / dock / markdown），为的是桌面版
  一键更新时的缓存命中——改一行界面不会让这些库跟着换哈希。

| | 改前 | 改后 |
| --- | --- | --- |
| 首屏字节 | 2813 KB（裸传） | 922 KB → 线上 **270 KB** |
| 终端模拟器 | 首屏 | 开出终端才下载 |
| 图表库 | 首屏 | 只在概览页的分片里 |

一条踩过的坑写在配置注释里：**图表库刻意不单独分组**。给它建组反而会让整块被
提升成入口的静态依赖，369 KB 的 recharts 就跟着首屏走了；交给打包器按可达性自动
切，它才安静地待在概览页的分片里。

### B2 应用外壳 —— 侧栏换路由不再抖

侧栏每次导航都拉一页 50 条会话再整棵重渲染，恰好发生在用户切会话、页面本来
最忙的那一刻。而绝大多数导航并不改变这份列表（点开一条已有会话最典型）。

改成拉回来先比一遍侧栏真正显示的字段，没变就留住原引用——React 直接不重渲染
（`setState` 拿到同一个值时会整体跳过）。导航项与最近会话项改 memo 计算。

### B3 对话区 —— 历史与实时分家、打字与流式各自安静

三处结构性问题：

**其一：流式期间每帧重建整份历史。** 流式时聊天状态每 80ms 换一次（分片合帧），
而历史在整轮里一动不动。原来两者在同一棵树里，于是每一帧都要为几百条历史重新
创建元素、走一遍协调——消息条自己的 memo 挡得住重渲染，但**元素创建与 diff 的
账照付**。抽出 `ChatHistory` 单独 memo，入参全是原始值与只随消息变的引用。

**其二：打字重渲整个输入区。** 草稿订阅原本挂在对话面板上，每个按键都重渲整个
面板，连带设置胶囊、分支选择器、附件盘、排队条（11 个组件全无 memo）。订阅下沉
进输入卡本身，面板不再参与；草稿 store 顺势归位到 `lib/chat/draft-store.ts`。

**其三：页面层每次渲染都新造一个 context 对象**，回调全是内联箭头——正文分片每
80ms 换一次状态，下游 memo 全部作废。命令面回调稳定化（要读实时状态的四个走 ref
转发），`useDraftSession` 的返回值补 memo，输入区八个组件加上 memo。

顺带把实时工具清单的四趟遍历合成一次 memo。

### B4 附属面板 —— 看不见的地方不该有消耗

查看器与子代理面板都消费聊天上下文，而它每 80ms 换一次引用——于是正渲染着几千行
代码的查看器、排着一列子代理的面板，每秒要白重建十几遍，**藏在别的 tab 后面
也照跑**。

- **查看器**：把跟随视图的订阅关进一个 24px 的开关组件，面板本体不再消费聊天
  上下文。顺带把五个 state 合成一份「带目标 key 的结果」——换文件不再先同步清空
  渲一帧（少一次渲染，也不闪旧内容），同时消掉了一条 `set-state-in-effect` 告警。
- **子代理面板**：整棵树按真实输入（条目 / 位置 / 展开项）记忆，聊天状态变化时
  返回同一个元素，React 直接跳过子树。

文件树已经是对的（`TreeNode` memo + 触碰集合按路径 key 记忆），日志面板与四个
git 面板也已经接了 `useVisibleLoad`（藏起来不轮询、不响应刷新广播，切回来补拉）
——这次核对确认无遗漏。

### B5/B6 列表页与边角

- **Intl 格式化器按语言缓存**。Intl 的构造是浏览器里最贵的动作之一——实测比复用
  一个实例慢 **30~50 倍**，而这几个函数都是按**行**调用的：列表每页二十行、消息流
  每条消息一次、通知中心每条通知一次、目录选择器每个文件一次。覆盖
  `formatRelativeTime` / `formatDateTime` / 目录选择器的修改时间 / 用量弹层的货币。
- **侧栏最近会话去掉三个点了没反应的菜单项**（继续 / 导出 / 删除从来没接过处理器）。
  按项目分组的那条主路径本来也没有这个菜单，会话管理在列表页。一并清掉随之失效的
  两条文案。

对全部按钮与菜单项做了一次机扫（无 `onClick` / `onSelect` / `render` / `submit`
的元素），除上面这三项外其余都是由 `DropdownMenuTrigger` / `AlertDialogTrigger`
提供处理器的触发器，没有第二处死交互。

## 怎么复现这些数字

```bash
# 接口耗时：单连接连打 40 次，取 avg/p50/p95（排除 curl 进程启动开销）
python3 - <<'PY'
import http.client, time
c = http.client.HTTPConnection("127.0.0.1", 48080, timeout=30)
h = {"Accept-Encoding": "gzip"}
path = "/api/sessions/76/git/overview"
for _ in range(5):
    c.request("GET", path, headers=h); c.getresponse().read()
ts = []
for _ in range(40):
    t0 = time.perf_counter()
    c.request("GET", path, headers=h); c.getresponse().read()
    ts.append((time.perf_counter() - t0) * 1000)
ts.sort()
print(f"{sum(ts)/len(ts):.2f} avg  {ts[len(ts)//2]:.2f} p50  {ts[int(len(ts)*0.95)]:.2f} p95")
PY
```

冷加载要先 `scripts/dev.sh restart server`（重建缓存在进程内存里）。

首屏字节量：`make build-web` 之后统计 `build/web/index.html` 直接引用（含
`modulepreload`）的全部文件，逐个 gzip 后求和。

> **验证带 SSE 的页面别用内嵌浏览器**：它每个 tab 的同域连接池极小，页面挂两条
> SSE 之后所有 fetch 会排队假死，看到的加载表现不作数。用 curl 或真实浏览器。

## 留给下一轮的

- **消息流虚拟滚动**（adr-002 M4 的遗留）。现在靠 `content-visibility:auto` 让屏外
  内容不绘制，但元素与 DOM 节点仍然全在。几千条的会话上，滚动仍有代价。
- **`git status` 的 31 ms** 是当前 git 面刷新的地板。真要再降只能换
  `--porcelain=v2 --branch` 把四条命令并成一条（省的是 CPU 不是墙钟），或者引入
  文件系统监听把「刷新」变成「被通知」。
- **h2c**：首屏 39 个文件在 HTTP/1.1 上要排几轮。本机可忽略，局域网访客场景下
  开 h2c 会更利索。
