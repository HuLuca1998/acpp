# ADR-013：通知体系

日期：2026-08-21　状态：已采纳

> **给 AI 协作者**：任何要「通知用户一件事」的功能，先读本文。全局调用接口见 [§全局调用](#全局调用怎么发一条通知)，新增通知种类的完整路径见 [§新增一类通知](#新增一类通知的完整路径)。载荷契约的字段表在 README §API 的「通知」小节，本文不重复。

## 背景

系统有两种客户端形态：owner 的 macOS 桌面壳（WKWebView），与局域网租户的浏览器（明文 http，adr-007）。会话里有四类值得打扰用户的事——agent 停下来等决策、有话要问、答完一轮、出错——外加一件所有人都关心的事：owner 一键更新替换了 .app，**别人的浏览器不会自己刷新**，接着用就是旧前端打新后端。

## 决策

### 1. 一条全局 SSE 流承载版本哨兵与通知

`GET /api/events`（`server/internal/httpapi/events.go`）：连上先收 `{kind:"hello", version}`，之后推 `{kind:"notify", ...}`。前端**单一连接**（`web/src/hooks/use-server-events.ts` 模块级单例）：版本哨兵与通知都听这一条，各连一条就是双倍连接与重连风暴。

版本探测**不轮询**：更新的本质是进程被换掉，这条流必断——断开本身就是信号。浏览器自动重连（服务端 `retry: 1500`），重连拿到的 hello 版本对不上基线就是更新过。轮询的发现延迟下限是轮询间隔，要秒级就得每页每秒打一次 health。

**关停即断流**：SSE 是不会自己收尾的在途请求，`http.Server.Shutdown` 对它只能干等超时——每次更新重启白白拖十秒。`main.go` 关停时先 `Hub.Close()` + `ChatService.CloseStreams()` 掐断全部流。实测 SIGTERM 重启到客户端拿到新 hello 共 **2 秒**。

### 2. 后端只广播，客户端决定弹不弹

「该不该打扰」取决于用户此刻在看哪一页、页面在不在前台——只有客户端知道。所以后端（`stream.Notice`）只如实广播「发生了什么」，判断在前端 `use-notifications.ts`：正盯着那条会话的页面不弹（界面上已有卡片）、偏好关掉的种类不弹。

投递按会话归属**精确匹配**（`Hub.Publish` 按 TenantID 路由）：租户互不可见；owner 也只收自己名下会话的——看得见（adr-007）不等于该被打扰。

### 3. 两端形式分道：macOS 系统通知 / 侧栏通知中心

- **桌面壳**：`UNUserNotificationCenter`（`desktop/macos/Sources/Notifier.swift`）。决策通知的按钮就是 agent 给的选项（动态 category，一条通知现注册一个），按下经 bridge 回前端走既有裁决 API——壳不重复实现 HTTP 客户端。授权由设置页发起，**不在启动时索要**。
- **浏览器**：侧栏底部的**通知中心**（`web/src/components/shell/notice-center.tsx`），配标题闪烁与 Web Audio 提示音。**弃用 toast 做通知**：弹一下就走的横幅留不住「有事等人处理」的信息，而租户可能几十分钟才回来看一眼。toast 只做操作的即时反馈。
- **为什么租户拿不到系统通知**：macOS 通知只发到 owner 那台机器；Web Notification 要 secure context，局域网明文 http 拿不到权限。这是形态约束，不是实现取舍。

macOS 两个实测坑（2026-08，macOS 26）：**app 必须在「应用程序」目录**，否则 `requestAuthorization` 返回 `Code=1` 且连系统弹窗都不出现；**一旦被拒再也弹不出来**，只能拉起 `x-apple.systempreferences:com.apple.Notifications-Settings.extension?id=<bundleID>`。ad-hoc 签名够用。设置页的权限卡（`web/src/components/settings/notifications.tsx`）对这两种情况都会如实说明。

### 4. 优先级制度与展示策略

优先级定义在 `web/src/lib/notify/store.ts`：**update > permission/elicitation > error > turn_end**。排序即展示——折叠态露出的永远是最该先看的：更新压倒一切（不刷新一切都是旧的），其次是 agent 停着等人的，出错要人知道但不阻塞谁，答完只是好消息。

展示（照 iOS 通知中心的图形语言与分工）：折叠态按视口高度平行显示 1–3 张卡、其余折成垫层；标题行（通知中心 + 角标）展开按会话分组的完整列表；**单卡点击直接执行动作**（update 刷新、会话通知跳会话——决策要拿主意本来就得看上下文，跳过去比就地摆按钮快）；hover 单卡出浮角 × 关那一条。动效：入场 280ms / 离场 240ms / 重排走 View Transitions。

### 5. 不落库、不重放

通知是「此刻值得看一眼」，错过的打扰没有补发价值；真正还悬着的事以会话页的卡片为事实源（那边由转录重建，才是持久层）。后端 Hub 无重放缓冲，前端存量是内存态（上限 20 条，刷新即清）。`permission_done` / `elicitation_done` 是撤回信号：事情在页面上处理掉了，两端挂着的那条通知都要收回去。

## 全局调用：怎么发一条通知

**后端**（任何 service 都可以）：装配层（`cmd/server/main.go`）建了唯一的 `noticeHub *stream.Hub`，要发通知的服务把它注入进来（参考 `ChatService.SetNotifyHub`），然后：

```go
hub.Publish(stream.Notice{
    Kind:      "notify",
    Event:     "turn_end",        // 见 Notice 注释里的取值
    SessionID: id, SessionTitle: title,
    Text:      summary,           // 一句话，调用方自己截断（chat 用 summarizeNotice）
    TenantID:  tenantID,          // 路由依据：0 = owner。填错 = 发给别人
})
```

`TenantID` 是唯一的投递路由，**不进 JSON**。与会话无关的全新事件域要先回到本文补决策，不要悄悄扩形状。

**前端**（本地产生的通知，如版本哨兵）：

```ts
import { pushNotice } from "@/lib/notify/store"
pushNotice({ id: "update", kind: "update", text: "v1.2.3", at: Date.now() })
```

同 id 覆盖（同一个请求重来不排两行）；`dismissNotice(id)` 撤回。**联调注入口**（仅 dev 构建）：浏览器控制台 `window.__acppServerEvent({ kind: "notify", event: "permission", sessionId: 1, ... })` 可伪造全局流事件走完整链路。

## 新增一类通知的完整路径

1. **后端**：在事件源头调 `hub.Publish`（会话域直接用 `ChatService.notify`）；新 event 值补进 `stream.Notice` 的注释。
2. **前端类型**：`web/src/types/acp.ts` 的 `NoticeEvent` 加值；本地种类加在 `lib/notify/store.ts` 的 `NoticeKind`。
3. **优先级**：`store.ts` 的 `PRIORITY` 表加一行——想清楚它比谁急。
4. **展示**：`notice-center.tsx` 的 `STYLES`（图标 + 色调）与 `TITLE_KEYS`；文案进 `i18n/locales/{zh,en}-notify.ts`。
5. **打扰判断**：`use-notifications.ts` 的 `TITLE_KEYS` / `wanted()`（挂到哪个偏好开关下）。
6. **文档**：README 通知字段表 + 本文该节。
